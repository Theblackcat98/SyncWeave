## Goal and accepted scope

Replace the Phase 1 simulation with a safe, testable **direct local-network send/receive flow** for user-selected files. The sender and receiver communicate directly on the local network; file bytes are not routed through a cloud service or unrelated relay. A compliant sender emits no file/transfer metadata before bilateral identity confirmation and emits no file body before the receiver accepts the exact pending session and selected file set. The receiver must make an explicit decision for every incoming transfer. Transfers must use safe destination writes, verify integrity, and recover clearly from cancellation, network failure, and process restart. These are application-protocol requirements, not a claim that a hostile peer cannot transmit bytes or that no hostile bytes reach the host, network interface, kernel, or socket buffers.

This follows Auri's current direction. LocalSend is a source of protocol and UX examples, **not a requirement to copy its wire protocol, stack, ports, concurrency limits, or identity model**.

### Explicit non-goals

- Ongoing two-way folder synchronization, deletion propagation, or automatic conflict resolution.
- Persistent pairing, durable peer trust, or auto-accept. A remembered destination or identity display is not authorization.
- Cloud relay or browser-link sharing.
- Treating a QR illustration, IP address, device alias, Favorite, or encrypted channel by itself as proof of peer identity.
- Declaring real transfer, filesystem safety, or recovery complete based on the existing mock TUI or its tests.

## Current baseline — not Phase 2 completion

The application is a deterministic in-memory simulation. Filesystem, peer, and transfer services are mocks; Favorites and transfer records reset with the process. The code has no real local-file access, LAN discovery/listener, byte streaming, authenticated peer transport, integrity verification, or durable recovery. Existing tests establish mock-UI behavior only.

Verified for this reconciliation on Bun 1.4.3 at the baseline commit: frozen-lockfile install, TypeScript typecheck, 16 automated tests, and the 9-test headless smoke script all pass. The working-tree source code was not changed. These checks are necessary but do not prove LAN or production readiness.

### Conditionally selected MVP profile

- **Bootstrap:** The user manually enters a numeric IP endpoint and port. This profile uses no mDNS, DNS-name resolution, or other automatic discovery; there is no hidden discovery fallback. Endpoint changes, redirects, stale addresses, or reconnects fail closed and require a fresh session.
- **Fresh peer identity:** Each session uses a newly generated ephemeral identity key and its complete Peer ID. The two users exchange and independently verify the full Peer IDs out of band; abbreviated IDs, device labels, and in-band claims do not count. Identity keys and IDs are never loaded from or written to durable peer storage.
- **Connection binding:** Establish the direct Noise-authenticated connection and validate its identity binding. Compare the complete expected Peer ID with `remotePeer` on that exact authenticated Noise `Connection`; only after exact equality may the application proceed, and all subsequent session traffic must use that same connection. Do not verify one connection and transfer over another. A mismatch or connection replacement aborts the session.
- **Consent ordering:** Both endpoint users independently confirm the matching session-bound identities before any peer/file application metadata is sent or accepted. After metadata review, the receiver must separately accept the exact pending session and selected file set before a compliant sender emits any file-body bytes. Gates B and C remain mandatory.
- **Ephemeral state and storage:** Session IDs, identity/confirmation state, and authorization are memory-only and are discarded on completion, cancellation, disconnect, or process exit; none may authorize a later session. Persist received content only within the user-chosen destination (including any temporary/partial file, on that destination filesystem); do not create a received-content cache or copy elsewhere.
- **Scope boundary:** This selection permits documentation and a separate scoped implementation PR only. It does not approve merging or release, waive any security/release gate, or establish product readiness. PR #14 remains documentation-only.

The selected profile is narrow and conditional, not blanket approval of a complete protocol stack, dependency configuration, every platform/network behavior, or production readiness. The exact pinned implementation must demonstrate the requirements below. Existing candidate research is evidence for test design only, not a substitute for implementation review or passing tests.

## Acceptance criteria

### 1. Direct transfer flow and consent

1. A user can choose one or more source files and send them to a reachable peer on the same local network. File bytes travel directly between the two devices; no cloud upload or relay carries them.
2. A receiver can explicitly start and stop availability. The UI shows whether its receive service is running and on which intended local interface(s); it does not start a hidden always-on listener.
3. For this MVP profile, a user connects only by manually entering a numeric endpoint; mDNS and other automatic discovery are disabled, not used as fallback. Connection failure is visible and does not trigger an undisclosed alternate endpoint or discovery method. Packet-capture and pre-confirmation disclosure checks in **Gate A** still apply.
4. Only after both endpoints independently confirm the matching session-bound identity under **Gate B** does the receiver see a transfer request. The request identifies the peer using the strongest **verified** identity available and shows requested names and sizes. The receiver can accept or decline each transfer; any multi-file subset acceptance is explicit and never authorizes unselected files.
5. **Gate C is separate:** a compliant sender emits no file body until the receiver explicitly accepts the exact pending session and selected file set. Discovery, peer selection, identity confirmation, a prior transfer, a saved destination, a fingerprint display, or peer presence never substitutes for current per-transfer consent. This constrains compliant sender behavior; receiver-side handling of unexpected frames is specified below.
6. Each accepted transfer has an unpredictable, short-lived session identifier and authorization scoped to the expected peer, session, and file. Wrong, expired, replayed, duplicate, or cross-session authorization is rejected.
7. Each file has legible states for queued, awaiting consent, transferring, verifying/finalizing, complete, skipped/rejected, cancelled, failed, and interrupted. Progress and byte counts reflect observed work; completion requires both integrity verification and finalization.

### 2. Transport, identity, and listener security

- Production transfer traffic is encrypted by default using a maintained security implementation. The sender verifies the intended receiver before emitting application-level peer/file metadata or file-body bytes; encryption to an unauthenticated endpoint is insufficient.
- The first-contact identity method is session-only and documented before implementation. A mismatch, expired session, or failed verification fails closed. Plaintext downgrade and permissive certificate bypass are not production defaults.

#### Gate A — Pre-confirmation discovery disclosure

The selected profile has no discovery: mDNS and all other automatic discovery are disabled. A numeric endpoint is entered directly by the user. Discovery is not identity confirmation and never authorizes peer/file metadata or a transfer. For any future separately reviewed discovery mode, before both endpoint users independently confirm the matching session-bound identity, only the minimum LAN discovery/control fields strictly needed to locate and open a candidate session may be visible; any identifier must be random, session-scoped, and unlinkable across sessions.

Before bilateral identity confirmation, discovery and session setup must not expose filenames, file counts or sizes, previews, content hashes, transfer requests, transfer identifiers or other transfer details, stable peer IDs, persistent keys/fingerprints, device labels, usernames, or account identities. This limit applies to mDNS and every alternative discovery mechanism; transport defaults are not an exception. If a chosen mechanism cannot suppress fields outside this minimum, disable or replace that discovery mode and use the approved manual fallback, or do not select that mechanism.

**Test:** Capture and decode traffic on the exact direct numeric endpoint when neither endpoint has confirmed, when only one endpoint has confirmed, and after both have confirmed. Verify that the selected profile emits no mDNS or other discovery traffic; before two confirmations, there is no peer/file application metadata, persistent identity, or transfer data. Record observed packet fields and endpoints; do not infer wire-level absence from application tests alone.

#### Profile source crosswalk (not evidence of passing or broad stack approval)

This source crosswalk supports test design for the conditionally selected manual-direct/Noise profile; linked specifications and source are not evidence of SyncWeave behavior or passing gates. The [Peer ID specification](https://raw.githubusercontent.com/libp2p/specs/master/peer-ids/peer-ids.md) derives Peer IDs from encoded public keys. A fresh Peer ID requires actually creating a fresh identity key pair before constructing that session's identity; it does not by itself establish unlinkability or hide other network metadata. The selected profile does not use mDNS.

- **Noise/Peer-ID identity gate:** The [Noise Framework](https://noiseprotocol.org/noise.html) leaves acceptability of the remote static key to the application. The pinned [noise-libp2p specification](https://github.com/libp2p/specs/blob/946441e549f2ce7bda3a9cc94a4690f26be2d384/noise/README.md) binds its presented identity key to its Noise static key with a signature; the [js-libp2p `Connection` API](https://github.com/libp2p/js-libp2p/blob/974e63f20688fdce0ab99c03aaaa1851013084c6/packages/interface/src/connection.ts) exposes that connection's `remotePeer` as a `PeerId`. For the selected profile, validate the required signature and compare the complete expected Peer ID, confirmed out of band, with `remotePeer` on the exact authenticated Noise `Connection`; only then proceed, using that same connection for the session. A wrong, stale, or spoofed expected peer must fail before a transfer stream opens or application data is sent or accepted. This is an application acceptance test, not a behavior established by the API alone.
- **Excluded mDNS source finding:** mDNS is not part of the selected profile. At maintained [`@libp2p/mdns` 12.0.33, js-libp2p commit `974e63f`](https://github.com/libp2p/js-libp2p/tree/974e63f20688fdce0ab99c03aaaa1851013084c6/packages/peer-discovery-mdns), the [README example](https://github.com/libp2p/js-libp2p/blob/974e63f20688fdce0ab99c03aaaa1851013084c6/packages/peer-discovery-mdns/README.md) shows a response with PTR, SRV, TXT, A, and AAAA records, including a sample SRV port. The [initializer](https://github.com/libp2p/js-libp2p/blob/974e63f20688fdce0ab99c03aaaa1851013084c6/packages/peer-discovery-mdns/src/mdns.ts) defaults to `_p2p._udp.local`, `224.0.0.251:5353`, and broadcasting unless disabled, and passes address-manager addresses to the responder. The [responder source](https://github.com/libp2p/js-libp2p/blob/974e63f20688fdce0ab99c03aaaa1851013084c6/packages/peer-discovery-mdns/src/query.ts) constructs PTR plus TXT answers containing `dnsaddr=<multiaddr>` for qualifying private/loopback multiaddrs with a Peer ID; it does not construct SRV, A, or AAAA records. Therefore the README's sample records/port are not evidence of the current source's wire output. This is a source comparison, **not a packet capture**.
- **LAN address-correlation caveat:** [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.txt) makes `.local.` names link-local, specifies mDNS on UDP 5353 and link-local IPv4/IPv6 multicast, and requires address records to be valid on the response interface. The responder's `dnsaddr=` TXT value can itself expose the configured address, transport/port, and Peer ID. A same-link observer may therefore correlate observed service announcements with local addresses and endpoints while those values persist, even when Peer IDs are fresh. This is a local-link, observed-fields caveat—not proof of a globally stable identity, reachability, or a privacy guarantee.

**Minimum profile acceptance gates (required, not evidence of passing):** (1) Test that each new session creates a fresh identity key before Peer-ID construction and neither loads nor persists a prior Peer ID/key. (2) Capture and decode actual direct-session traffic using the pinned dependency versions, runtime, and target interfaces; record endpoints and observed fields, verify no mDNS/automatic-discovery traffic, and prove no peer/file application metadata is sent or accepted before bilateral confirmation. Packet capture remains required; a source review or application test is not a substitute. (3) On the exact Noise-authenticated `Connection`, test full Peer-ID equality against the out-of-band expected identity and prove a mismatch, stale identity, or replacement connection opens no transfer stream and sends/accepts no application data. Gate B's independent user confirmations and Gate C's separate receiver acceptance remain mandatory.

#### Protocol-agnostic session authorization gates

These gates are mandatory regardless of the eventual reviewed profile; they do not select a transport, protocol, or cryptographic composition.

1. **Transcript-bound identity confirmation:** Both endpoints display the same session-bound confirmation derived from the same authenticated session transcript for the intended peer and transfer. An identity or transcript mismatch, expired confirmation, or confirmation from another session fails closed. **Test:** verify matching confirmations for the intended session; force an identity/transcript mismatch and assert that compliant endpoints emit no application-level peer/file metadata or file body, and that the receiver does not consume unauthorized frame bodies.
2. **Role, version, nonce, peer, and session binding:** The confirmation and all subsequent authorization are bound to sender/receiver roles, the profile and version specified by the eventually reviewed profile, the complete expected and authenticated peer identities, a fresh unpredictable per-session nonce, and a unique transfer session. **Test:** swap roles, alter the profile/version, change either peer identity, reuse/change the nonce, or change the session identifier; each case must invalidate the confirmation/authorization and fail closed. Until a profile is reviewed, profile-dependent tests remain blocked or unverified.
3. **Gate B — Two independent out-of-band identity confirmations before peer/file metadata:** Each endpoint's user must independently compare and confirm the matching session-bound value using the specified out-of-band method; one user's action cannot stand in for the other's. A compliant sender emits no peer/file application metadata (including peer/device identity claims, filenames, file counts/sizes, previews, or a transfer request) before both confirmations succeed. Before confirmation, the receiver may accept only bounded handshake/discovery fields needed for session establishment and expressly allowed by Gate A; it rejects other frame types as specified under **Receiver parser: state-first, header-before-body** below. After matching confirmations, peer/file metadata may be presented for review. **Test:** capture both directions with zero, one, and two out-of-band confirmations; assert that a compliant sender emits no peer/file metadata with zero or one confirmation, the receiver accepts only the pre-confirmation allowlist, and a mismatch aborts before peer/file metadata is accepted or file content is consumed.
4. **Gate C — Separate receiver acceptance before bytes:** Only after both identity confirmations and presentation of the transfer request may the receiver explicitly accept the exact pending session and selected file set in a distinct action. Discovery, peer selection, and identity confirmation are not transfer consent. **Test:** assert that a compliant sender emits no file-body bytes before this separate acceptance, including after an earlier transfer; decline, timeout, or acceptance for a different session/file set causes no compliant file-body emission. Test hostile early file frames separately under **Receiver parser: state-first, header-before-body**; do not turn this sender rule into a claim that no hostile bytes reach the host.
5. **Replay, downgrade, and stale-peer rejection:** Reject replayed, duplicated, expired, or cross-session confirmations, authorizations, and transfer messages; reject fallback to an unapproved version or plaintext; invalidate discovered peers after a network, interface, or local-address change until rediscovered. **Test:** exercise each case and assert fail-closed behavior: compliant endpoints emit no unauthorized peer/file metadata or file body, and the receiver consumes no unauthorized frame body; stale peers cannot initiate a transfer.
6. **Redirect and 0-RTT fail-closed:** Any redirect during session establishment terminates the session; do not automatically follow or retry at a different endpoint. Reject 0-RTT or other replayable early application data; do not send or accept peer/file metadata or file bytes through it. **Test:** inject a redirect and an early-data attempt and assert session failure, no compliant sender emission of peer/file metadata or file body to the redirected endpoint, and no unauthorized receiver-side application consumption. This does not imply absence of hostile wire/socket bytes; report those only if measured.

#### Receiver parser: state-first, header-before-body

At the application framing layer, the receiver first reads only a fixed-size, bounded frame header. It validates the frame type, declared body length, and current protocol state before requesting, allocating, decoding, or otherwise consuming that frame's body; it must not use a whole-frame buffering/parsing helper before consent checks. Before bilateral identity confirmation, the receiver accepts only bounded handshake/discovery fields needed for session establishment and permitted by Gate A. Gate A remains the separate, explicit rule for what discovery may disclose. Any frame type not allowed in the current state—including file/transfer metadata before bilateral confirmation or a file-body frame before the receiver's exact per-transfer acceptance—is rejected and the session closed before the application parser requests or consumes its body. For a protected field in a bounded streaming header, reject an unknown key as soon as it is recognized and, where framing permits, before consuming or decoding its associated value. A strict-schema check after parsing the complete header or calling `JSON.parse` proves only that the unknown field was not accepted downstream; it does not prove the metadata was not parsed. Rejected body bytes must not be decoded, admitted to authorized transfer state, staged/persisted, or written/finalized at the destination. Enforce per-frame and aggregate handshake/discovery bounds and timeouts; oversized or malformed headers fail closed before body reads. These are receiver application-layer guarantees: rejection cannot prevent a hostile sender from transmitting bytes, nor retract bytes already yielded by the source or buffered by the transport or lower layers.

**Adversarial acceptance tests:** (a) With neither user confirmed and with only one user confirmed, inject an unexpected early-metadata frame whose header declares a body, including an oversized declared body; assert the receiver rejects on the header, closes without invoking a body read or allocating a body buffer, and does not decode, admit to state, stage, persist, or destination-write the unauthorized body. (b) After bilateral identity confirmation but before receiver acceptance, inject a file-body frame; assert the same header-first rejection and no body decoding, admission to transfer state, staging/persistence, or destination write. (c) In the isolated two-peer harness, inject (i) an otherwise valid `session-open` carrying an unknown protected key, (ii) an otherwise valid `identity-confirmation` carrying one, and (iii) each message with the other message's protected fields piggybacked (for example, identity-confirmation fields in `session-open` and session-open fields in `identity-confirmation`). Verify rejection as early as the bounded streaming header permits and before consuming/decoding the associated value when the framing allows it. A test that only checks strict-schema rejection after `JSON.parse` establishes downstream non-acceptance, not early parser rejection. Instrument source yields and the framed reader so tests distinguish bytes already yielded from bytes consumed by the parser and prove whether the body-read path was invoked; checking only final file state or relying on a compliant sender is insufficient. Also test allowed bounded handshake/discovery frames and their limits. These tests establish receiver application behavior, not prevention of hostile transmission.

**Byte accounting and claims:** Report separately, with the observation point, units, and method: (1) source-yielded bytes, meaning bytes delivered by the instrumented source (including body bytes already yielded); (2) parser-consumed bytes, meaning bytes the frame parser logically advances over, with header and body counts separate and excluding bytes merely present in a source/read buffer; (3) decoded body output bytes (and, if decoding transforms the representation, encoded body input bytes separately); (4) body bytes admitted to authorized transfer state, counted at admission rather than later persistence; (5) bytes staged/persisted to temporary storage; and (6) bytes written to the final sink/destination. If instrumented, also report socket-read and packet-capture/wire bytes as distinct counters; label every uninstrumented boundary **not measured**. Do not infer one layer's count from another. For rejected adversarial bodies, assert zero body bytes consumed by the parser, decoded, admitted to transfer state, staged/persisted, or written to the sink; source-yielded, socket-read, and wire counts may be nonzero and must be reported as measured or **not measured**. A receiver rejection cannot prevent the hostile sender from transmitting bytes already yielded or buffered below the application layer. Do not make any zero-wire-byte or zero-host-byte claim unless that exact boundary was directly measured.

- Peer announcements, names, addresses, metadata, and request bodies are untrusted. Requests have bounded sizes and timeouts, rate/connection limits, and deterministic cleanup after rejection, cancellation, disconnect, or malformed input.
- Listener bind scope and lifetime are deliberate, visible, and stoppable. Tests from another host confirm the service is not unintentionally exposed beyond intended local-network interfaces.
- A threat model covers hostile peers on shared Wi-Fi, spoofed discovery, wrong first-contact identity, replay, malicious metadata/names, resource exhaustion, and local privilege boundaries. Logs contain no file contents, tokens, or unnecessary private paths.
- Before implementation, set numeric caps for discovery queries/announcements, candidate peers, connection/stream opens, concurrent streams, and per-stream/session bytes and rates. Test at and above each cap, including discovery and stream floods; verify excess work is rejected or dropped with bounded memory/CPU/queues and deterministic cleanup. Derive the limits from SyncWeave's goals rather than copying upstream defaults.

### 3. Safe writes and integrity

- Peer-supplied names and metadata cannot select paths outside the user-selected destination. Validate separators, absolute/traversal paths, reserved or incompatible names, invalid Unicode, hidden-name cases, and length limits. Collision handling is predictable and visible; symlinks and races cannot redirect a write outside the destination.
- Stream with backpressure; do not load whole files into memory. Enforce agreed file/session/request/connection/temp-storage limits and fail clearly on insufficient space or permissions.
- Receive each file into a temporary file within the user-chosen destination, on that destination filesystem. Do not persist received content elsewhere. Verify expected byte count and a cryptographic content hash, then finalize with a platform-safe atomic rename or equivalent. A partial or mismatched file is never marked complete or left under its requested final name. **A content hash detects corruption; it does not authenticate the peer.**
- On failure or cancellation, remove temporary content safely or retain it only as a clearly identified recoverable partial. Never execute or auto-open received content. Arbitrary extensions remain transferable; safety comes from inert storage, path validation, resource limits, and explicit user action.

### 4. Cancellation, retry, and recovery

- Test cancellation before metadata, while consent is pending, during each file, after the last byte but before verification/finalization, and after one file completes in a multi-file request. Both peers converge on a clear status and release listeners, slots, streams, timers, and temporary files.
- Retry is bounded and user-visible. The selected retry/resume policy prevents duplicate final files and never trusts an unverified client-reported offset. If Phase 2 restarts a file from byte zero, the UI says so; resumability is not implied.
- Wi-Fi/address change, sleep/resume, listener failure, sender/receiver termination, and restart produce a deterministic outcome. On restart, all memory-only identity, session, confirmation, and authorization state is gone: pending sessions cannot resume or authorize bytes. Completed and incomplete destination files are distinct; abandoned temporary files are safely cleaned or labelled; any continuation requires a fresh session, full out-of-band identity verification, bilateral confirmation, and receiver acceptance. No partial transfer is reported as successful.
- Session IDs, identity keys/IDs, confirmations, authorization tokens, and any state capable of resuming or authorizing a session are never persisted. Persist only non-authorizing local transaction information strictly required by the separately approved recovery policy, if any; define its retention and privacy before doing so. Received content, including partial content, remains only within the user-chosen destination. Persistent peer pairing, durable peer authorization, and implicit future acceptance remain out of scope.

## Phase 2 exit definition

Phase 2 is complete only when the decisions above are recorded, every applicable criterion has reproducible evidence, real two-device LAN transfers pass the supported platform matrix, and incomplete/failed transfers cannot be mistaken for completed files. A mock-only test, green CI run, loopback transfer, or one-device demo is insufficient on its own.

## LocalSend and security references

LocalSend's published v2.2 protocol describes metadata preparation followed by a receiver decision, direct uploads using session/file tokens, optional SHA-256 verification, and cancellation. Its current v2 server code provides examples of session checks and cleanup. These behaviors inform but do not dictate SyncWeave's design.

- [LocalSend Protocol v2.2](https://github.com/localsend/protocol) — discovery, metadata-only preparation, receiver acceptance/rejection, file upload, cancellation, and optional checksum.
- [LocalSend v2 receiver implementation at inspected commit `14f3a87`](https://github.com/localsend/localsend/blob/14f3a87426eedffaa9d87d011132eca5501abeb8/packages/core/src/http/server/v2.rs) — session/file-token validation, sender binding, checksum handling, cancellation, and cleanup patterns.
- [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) — untrusted filenames, length/upload limits, storage, and safe handling. This is adapted for arbitrary-file transfer without an extension allowlist.
- [OWASP Transport Layer Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html) — transport confidentiality/integrity and the need to authenticate the intended peer.
- [OWASP Pinning Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Pinning_Cheat_Sheet.html) — pinning is threat-model dependent and requires a tested key-rotation/recovery path.

**Reference caveat:** LocalSend's port, multicast group, API, concurrency model, optional PIN, browser route, and trust details are not SyncWeave requirements. Any selected SyncWeave defaults require their own decision and evidence.
